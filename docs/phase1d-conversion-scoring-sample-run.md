search-intent fit — those still require a human pass.

## What the "revise" scores actually mean (read before acting on them)

The four non-blog pages (resource hub, product, collection, landing)
all failed `audience_clarity`, `funnel_stage_clarity`,
`cta_relevance_benefit_clarity`, and `lead_offer_fit`. **This is not a
content quality problem** — it's because `BHP_Content_Classification`
(Workstream 2) only classifies blog *posts*, by design; it has no
lookup path for a WooCommerce product, a WordPress Page, or a shortcode-
rendered landing page. Those criteria will always fail on non-post
content until (a Page/product-level classification bridge is deliberately
built as future work, or (b) the criteria are made page-type-aware the
way `product_relevance` already is. **Do not "fix" these 4 pages by
force-classifying them** — fix the scoring framework's coverage instead,
in a future phase.

The two blog posts also failed the `accessibility` proxy check (at least
one `<img>` on each is missing meaningful `alt` text) — this is a real,
actionable finding, but per the no-bulk-auto-edit rule this report does
not touch those images. Flag for a future, deliberate accessibility pass.

## Honest limitations of this sample run

- `accessibility`, `claim_accuracy`, and `performance_risk` are proxy
  heuristics (documented per-criterion in `BHP_Conversion_Scoring::criteria()`),
  not full audits. A `pass` here does not mean a real a11y/Lighthouse/
  editorial review was performed.
- `mobile_usability`, `visual_readiness`, and `search_intent_match`
  were not scored at all in this run (no manual override was supplied)
  — their `state` is `null`, not a passing score. See
  `.claude/rules/testing.md` for how those should actually be verified (real
  device/viewport, real screenshot review).
- This run fetched live HTML via `wp_remote_get()` from the server
  itself — read-only, no login, no data written.
