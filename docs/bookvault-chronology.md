# Bookvault Status Chronology

How the dashboard determines Bookvault fulfillment-routing status per
order, and why. Originally written during the Phase 5 KPI reconciliation
pass (2026-07-06); substantially revised the same day after a **direct
reconciliation against the Bookvault portal** revealed the dashboard's
Bookvault denominator was inflated by orders that were never actually
expected to route. Source: `BHP_Bookvault_Status`
(`includes/dashboard/class-bhp-bookvault-status.php`) and
`BHP_Order_Metrics::bookvault_fulfillment_status()`
(`includes/dashboard/class-bhp-order-metrics.php`).

## The discrepancy Andrew reported, and what caused it

The dashboard showed "6 Bookvault-eligible orders, 2 routed, 4 needing
attention, 33.3% routing success" while Andrew observed only **3** orders
in the Bookvault portal itself. Direct inspection of the Bookvault
Orders page (`https://portal.bookvault.app/Orders`, read-only, Andrew's
own authenticated session) confirmed exactly 3 orders exist there:

| Bookvault ref | Your Ref (Bookvault's own field) | Belongs to this WooCommerce store? |
|---|---|---|
| 2796848 | `WC-2724-355` | Yes — order #355 (automatic) |
| 2796764 | `WC-2724-353` | Yes — order #353 (automatic) |
| 2793822 | `43908-#00001` | Yes — order #336 (**manual** — see correction below) |

**Correction (2026-07-06, order-provenance audit)**: this row was
originally assessed as "No — different reference format and a different
personal email address than this store's business address, not from this
site's order sequence at all," on the theory that a non-matching reference
format meant an unrelated store. **Andrew has since directly confirmed
this was wrong**: `BV2793822` / `43908-#00001` IS this store's order
#336 — Andrew's own first Mariana Trench paperback fulfillment test, which
did not route to Bookvault automatically and which he entered into
Bookvault manually afterward. A manually-created Bookvault record
naturally has a different reference format than an automatically-created
one (it was never generated by the WooCommerce→Bookvault plugin
integration at all), which is exactly what caused the earlier
misclassification. See `docs/order-provenance-audit.md` for the full
correction and evidence.

So Bookvault's own records show **exactly 3 real orders from this
store**, not 6: 2 created automatically (#355, #353, both already
correctly showing as routed) and 1 created manually (#336). The remaining
3 orders the old dashboard flagged (#351, #322, #317) were never real
Bookvault orders at all, for different reasons (see the reconciliation
table below). The dashboard was counting all of them (plus #336) anyway
because its old eligibility check only asked "is this a paid order
containing a catalog product," never "is this order actually still
expected to fulfill via Bookvault right now" — and, separately, had no
way to represent "fulfilled manually" at all before this correction.

## Why order notes (and now `BVRef` postmeta) are the sources used

Bookvault does not expose routing status via a dedicated database table
(confirmed by direct inspection: no `%bookvault%`/`%bvlt%` table exists).
It DOES write one structured postmeta key, `BVRef`, on any order it
actually creates — confirmed present only on #355 (`BVRef=2796848`) and
#353 (`BVRef=2796764`), and absent on #351/#336/#322/#317. This makes
`BVRef` the strongest available local signal that a real Bookvault order
exists, stronger than parsing note text (see the source-of-truth
hierarchy in `docs/kpi-definitions.md`).

Beyond `BVRef`, the only trace of *what happened* is the order note
Bookvault itself writes. **Three** real patterns are now recognized
(previously two — see the correction below):

- **Success**: `Order saved with status Active as BV2796848` or
  `Order saved with status Draft as BV2796764`
- **Excluded** (new): `Failed to read line_items: Notice - The Bookvault
  plugin scans all incoming orders to identify those specifically
  intended for Bookvault to fulfill. Based on your current configuration,
  this order does not indicate Bookvault as the selected fulfillment
  service. As a result, it will not be processed by Bookvault.`
- **Failure** (genuine technical error, distinct from Excluded): any
  other `Failed to read line_items:` message that does NOT contain the
  "not selected as fulfillment service" text.

If Bookvault ever changes its own note wording, these patterns stop
matching and the order reports `unknown` — never a false positive.

## Correction: "Excluded" was previously misclassified as "Failed"

Order #351's three notes all match the pattern above starting with
"Failed to read line_items:" — but the actual message text says Bookvault
**intentionally declined** to process the order because it wasn't flagged
for Bookvault fulfillment. This is not a technical error and nothing
needs to be resent. The dashboard's original `FAILURE_PATTERN` regex
matched on the "Failed to read line_items" prefix alone, without checking
what the rest of the message actually said, so it classified this
intentional exclusion as a generic technical failure requiring action.
`EXCLUDED_PATTERN` is now checked first and specifically matches the "not
selected as fulfillment service" / "will not be processed by Bookvault"
wording, so this case is now labeled `excluded`, not `failed`.

**Note on prior documentation**: an earlier phase of this project
described order #351 as "a historical failure/manual-intervention case…
automatic retries failed… a manual resend was eventually required."
Today's direct inspection of order #351's actual, current order notes
shows three identical "excluded — not configured for Bookvault" messages
and **no success note ever**, and #351 does not appear in Bookvault's own
order list at all. This directly contradicts that earlier characterization.
Rather than silently overwrite that history, it's flagged here explicitly:
**this document's current description of #351 is based on today's direct
observation of its live order notes and the live Bookvault portal, not on
the earlier summary.** If a resend genuinely happened at some point and
succeeded, no evidence of that success remains in this order's notes or
in Bookvault's own records today — worth Andrew independently confirming
if the discrepancy matters to him.

## Legacy / pre-integration orders

Orders #336 and #322 (both paid 2026-07-02) have **zero** Bookvault-related
notes or `BVRef` postmeta on the WooCommerce side — not success, not
excluded, not failure. Compared against #351/#353/#355 (all paid
2026-07-05, all with at least one real Bookvault note), this is strong
evidence that Bookvault's automated order-scanning simply wasn't wired up
yet on 2026-07-02, for both orders. For #336 specifically, this silence on
the WooCommerce side is expected for a *different* reason too: its
Bookvault record was created manually by Andrew directly in the Bookvault
portal (ref `BV2793822`), which never touches WooCommerce order notes or
postmeta at all — see the correction above and
`docs/order-provenance-audit.md`. #336 is correctly excluded from the
automatic-routing denominator either way, but is still counted as a real,
manually-fulfilled Bookvault record in the dashboard's separate
"Bookvault records" summary. `BHP_Bookvault_Status::
INTEGRATION_LIVE_SINCE` (2026-07-04 00:00:00 site-local) is a conservative
boundary set between the last confirmed no-note order and the first
confirmed noted order. Orders paid before this cutoff with no Bookvault
note are classified `legacy_pre_integration` — excluded from the routing
denominator and never flagged, because no automated attempt was possible
at the time. **This is an approximation, not an exact go-live record** —
update the constant if Andrew has a precise timestamp for when the
Bookvault integration actually went live.

## Refunded orders

Order #317 was paid and fully refunded **24 minutes later**, with the
refund reason recorded as `"Test-mode refund verification"` — i.e. this
was itself a test transaction, not an organic customer refund. It has no
Bookvault notes and no `BVRef`. A fully refunded order is not expected to
fulfill (see `docs/kpi-definitions.md`'s fulfillment-eligibility rules),
so #317 is now excluded from the Bookvault denominator with reason
`refunded`, and its historical routing status (never attempted) remains
visible in the recent-orders table rather than silently disappearing.

## Chronology, not "any failure ever"

The chronology engine (`get_status_from_events()`) walks every
Bookvault-related note in order and lets the **latest** event decide the
current `status` (`routed` / `excluded` / `failed` / `unknown`), while
still recording:

- `had_prior_success` — true if a success ever occurred before the
  current (possibly failed) latest state — distinguishes "never routed"
  from "routed once, then something broke again."
- `bookvault_state_is_draft` — true when the LATEST success is still
  "Draft," not yet promoted to "Active." Both count as `routed` for the
  routing-success-rate KPI, but the dashboard's fulfillment-summary table
  now shows Active and Draft as separate line items.
- `seconds_to_route` — always measured from payment to the **first**
  success note, regardless of any later failure.
- `failure_count` — total genuine failure notes, never incremented by an
  `excluded` event.

## What each field means

| Field | Meaning |
|---|---|
| `status` | `'routed'` \| `'excluded'` \| `'failed'` \| `'unknown'` — reflects the LATEST relevant note, or `'routed'` unconditionally if `BVRef` postmeta is present (see source-of-truth hierarchy) |
| `bookvault_ref` | The Bookvault reference from the LATEST success note, or from `BVRef` postmeta if no note parsed one |
| `bookvault_state` | Bookvault's own status word: `Active`, `Draft`, or `Unknown` (when `BVRef` exists but no note supplied a state word) |
| `bookvault_state_is_draft` | `true` when the latest state is still Draft |
| `had_prior_success` | `true` if any success occurred before the current latest state |
| `failure_count` | Total genuine failure notes across all time (excludes `excluded`-type events) |
| `first_note_time` / `last_note_time` | ISO 8601 timestamps of the earliest and latest Bookvault-related note |
| `seconds_to_route` | Time between `$order->get_date_paid()` and the FIRST success note, in seconds |

## Fulfillment-expectation decision (see `BHP_Order_Metrics`)

An order only counts toward the routing denominator ("expected") if it is
catalog-eligible AND not fully refunded AND not cancelled AND not
Bookvault-excluded AND not legacy/pre-integration — UNLESS `BVRef` proves
a real Bookvault record exists, in which case it's always counted as
expected/created regardless of what happened afterward (the historical
routing record is never erased by a later refund). Full rule and priority
order in `docs/kpi-definitions.md`.

## Manual attention ("orders needing attention now")

An order is flagged as needing attention only when it is **expected**
(per the above) AND:

- The latest event is a genuine failure (`status === 'failed'`), **or**
- No Bookvault record exists at all and more than 15 minutes have passed
  since payment (`BHP_Order_Metrics::ROUTING_FAILURE_THRESHOLD_MINUTES`).

Excluded, refunded, cancelled, and legacy/pre-integration orders are
**never** flagged, no matter how much time has passed, because they were
never expected to route in the first place — this was the direct cause of
the old dashboard's false "4 orders needing attention."

## Reference orders used to validate this logic

- **Order #355** — a confirmed clean success: paid, routed to Bookvault
  with a single Active note, `BVRef=2796848` present, no failures.
- **Order #353** — a confirmed clean success still in Draft:
  `BVRef=2796764` present, Bookvault's own note says "Draft," not yet
  "Active." Demonstrates the Draft-vs-Active distinction independent of
  #355's Active example.
- **Order #351** — see the correction section above: three identical
  "excluded" notes, no `BVRef`, does not exist in the Bookvault portal.
  Used to validate the `excluded` classification and to confirm it is
  correctly removed from the action-required count.
- **Order #322** — zero Bookvault notes, paid before
  `INTEGRATION_LIVE_SINCE`. Used to validate the legacy/pre-integration
  exclusion.
- **Order #336** — zero Bookvault notes on the WooCommerce side (same
  automatic-routing exclusion as #322), but a REAL, manually-created
  Bookvault record exists for it (`BV2793822`, confirmed by Andrew
  2026-07-06). Used to validate that a manually-fulfilled order is
  correctly excluded from the automatic-routing denominator while still

- **Order #317** — fully refunded 24 minutes after a test-mode payment, no
  Bookvault notes. Used to validate the refunded-order exclusion.

No customer data (name, address, email) is read or displayed anywhere in
this logic — only order IDs, note timestamps, and note text matched
against the patterns above.

## Direct Bookvault connectivity assessment (Phase 8)

What's actually available today, assessed read-only during this
reconciliation pass:

- **Data source**: (1) `BVRef` order postmeta, written by the Bookvault
  WordPress plugin (v6.0.0, active) at order-creation time — structured,
  reliable, but only tells you a record exists, not its current state.
  (2) WooCommerce order notes the same plugin writes — the only source
  for state words (Active/Draft) and for the excluded/failure distinction,
  but they're a point-in-time log, not a live status feed. (3) The
  Bookvault web portal itself (`portal.bookvault.app`) — authoritative,
  but only accessible via a human logging in; no API credentials exist in
  this project.
- **Fields available locally**: `BVRef` only (no dispatch date, no
  tracking number, no cost breakdown beyond what's visible in the
  Bookvault portal's own Orders list, which is UI-only).
- **Authentication model**: the Bookvault *plugin* authenticates to
  Bookvault's backend using its own stored credentials (not inspected or
  touched this pass — out of scope and unnecessary for a read-only
  postmeta/note check). No separate API key exists for this project to
  use directly.
- **Current status values observed**: `Active`, `Draft` (from notes); the
  Bookvault portal's own UI additionally shows Created/Approved/In
  Progress/Printed/Packed columns (visible in the Orders list screenshot)
  that have **no corresponding webhook, note, or postmeta on the
  WordPress side** — those states are portal-only today.
- **Tracking/dispatch fields**: none available locally, confirmed absent.
- **Costs available**: the Bookvault portal's Orders list shows a
  print/unit cost per order and a total order cost — visible only in the
  portal UI, not synced anywhere locally. Not used in this pass's
  estimated-profit figures (see `CSO_PRIVATE_REFERENCE.md` for the private
  cost-sources doc).

  **Correction (2026-08-03, owner-approved).** Two example dollar values
  previously shown in this bullet have been removed. Per-unit printing costs
  and per-order shipping costs are private business figures and do not belong
  in this repository, which is public. The removed text, together with its
  full context, provenance and dates, is preserved privately in the company's
  Business OS records at `VENDOR-AND-SUBSCRIPTION-REGISTER.md` section 6 — the
  values themselves are deliberately not restated here. The structural fact
  this bullet exists to state is unchanged: those columns are visible in the
  Bookvault portal UI only, and are not synced anywhere locally. Note also
  that this file is not listed in `docs/AI_CONTEXT_INDEX.md` and is therefore
  not canonical for anything; the authoritative cost sources are named in the
  private records referenced above.
- **Rate limits**: unknown — no direct API access exists to test against.
- **Read-only synchronization feasibility**: feasible in principle if
  Bookvault exposes a documented read-only API (not confirmed either way
  this pass — no API credentials were requested or created, per
  instruction). The safer, immediately available option is a manual or
  scheduled **export-based reconciliation**: periodically export the
  Bookvault portal's Orders list (CSV, if supported) and diff it against
  `BVRef`-tagged WooCommerce orders to catch any order Bookvault created
  that never got its `BVRef` written back correctly, or vice versa.
- **Bookvault as direct source of truth**: not yet, and not implemented
  in this pass. `BVRef` postmeta is the best proxy currently available
  for "Bookvault created this order," but true current-state fields
  (Printed/Packed/Dispatched) require either a documented Bookvault API
  or a recurring manual export-and-diff process. This is intentionally
  scoped as a **future improvement**, not built now.

## What this deliberately does NOT claim

Per the explicit instruction not to invent shipment/tracking state: this
dashboard has no reliable source for "in production," "shipped," or
"delivered" status. There is no Bookvault tracking webhook or API
integration — see `docs/kpi-definitions.md`'s connectivity-assessment
notes for what would be required to add one. The "Bookvault fulfillment
summary" table on the dashboard only ever shows: Active / Draft / Awaiting
routing / Action required / Excluded (with reasons). Anything beyond
that — including tracking numbers, estimated delivery, or dispatch
status — must be checked directly in the Bookvault portal, and the
dashboard says so explicitly rather than guessing.
