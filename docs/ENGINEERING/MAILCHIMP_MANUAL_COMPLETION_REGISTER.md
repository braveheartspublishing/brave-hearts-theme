## Purchase-tagging architecture verification (2026-07-16, proven via a controlled staging test)

- **Source integration**: the Mailchimp for WooCommerce plugin syncs orders to Mailchimp's Orders API via an Action Scheduler job queued from the `woocommerce_order_status_changed` hook (`handleOrderStatusChanged()` in `class-mailchimp-woocommerce-service.php`), specifically when an order transitions from `pending` to `processing` or `completed`. The job is queued to start ~90 seconds after the transition — confirmed directly in the plugin's own debug log (`wc-logs/mailchimp_woocommerce-*.log`), not inferred.
- **The automation that applies the tag**: `Global - Tag Purchasers` (id 88), Active, trigger "Contact buys any product from your store," single action "Add tag Customer - Purchased."
- **Proven via a controlled, Andrew-authorized staging test (2026-07-16)**: a WP-CLI-created guest WooCommerce order (staging order #595, non-admin, test contact `suppression-test-contact-01` — a made-up address at the company's own domain, not a real inbox or subscriber) was transitioned to `Processing` via the WooCommerce order API. The Mailchimp sync fired on schedule, the contact was created in Mailchimp (synced as subscriber status "transactional," i.e. not opted into marketing), and `Global - Tag Purchasers`'s live Flow Data showed **1 contact started, 1 completed, tag added: 1** — confirmed independently by viewing the tag's own contact list, which showed the test contact with the `Customer - Purchased` tag, Revenue $11.99, Orders 1. **This proves the purchaser-tagging pipeline works correctly end to end for a real (non-admin) contact, and that it fires regardless of the contact's marketing-subscription status.**
- **Scope — directly observed and now Frozen (see `FUNNEL_CONSTITUTION.md`)**: the trigger condition is "buys **any product**," not Collection-only. Andrew has explicitly ratified this as the permanent rule (2026-07-16): any valid purchase suppresses the acquisition coupon path. **No longer a REQUIRES ANDREW DECISION item — do not reopen.**
- **Sync timing — measured, not estimated**: the Mailchimp-for-WooCommerce plugin queues its sync job for ~90 seconds after the order-status transition (confirmed in the plugin's own log). On this low-traffic staging environment, that queued job does not run until something triggers WordPress's cron (a real site visit, or an explicit `wp action-scheduler action run`) — during this test the job was manually forced to run via WP-CLI rather than waiting for organic traffic, since staging otherwise receives too little traffic to trigger WP-Cron promptly. **Production almost certainly receives enough real traffic that this delay is a non-issue in practice**, but this is a real operational nuance worth knowing: a staging-only test with no forced cron run could sit queued indefinitely. Once the job ran, the full observed pipeline (order sync → contact creation → tag application) completed within roughly 2–3 minutes of the original status transition.
- **Exclusions — carried forward from a prior session's evidence, not re-tested this session**: orders placed while logged in as WordPress user #1 (Administrator) are skipped from Mailchimp sync entirely — confirmed on 5 historical orders including one Completed order. **Administrator test purchases must not be used as proof the pipeline works** — this session's test deliberately used a guest order (`customer_id = 0`), not an admin-logged-in order, precisely to avoid this exclusion.
- **Refund/cancellation handling — now tested and confirmed, not assumed**: after the primary test succeeded, the same test order (#595) was cancelled via the WooCommerce order API. The cancellation synced to Mailchimp's own order record (`updateStoreOrder` in the plugin log), but **the `Customer - Purchased` tag was NOT removed** — the contact still shows the tag after cancellation. Confirmed directly, not inferred: `Global - Tag Purchasers` only has an "add tag" action, no corresponding "remove tag" logic exists anywhere in the account. **A refunded/cancelled purchaser remains suppressed from acquisition coupons indefinitely under current behavior.** See `FUNNEL_CONSTITUTION.md`'s Post-Purchase Target State for the resulting open decision.
- **Returning-purchaser re-entry into acquisition journeys**: **still not verified.** Whether a contact who is tagged `Customer - Purchased` and later re-triggers an acquisition journey (e.g. re-downloads a different audience's lead magnet) would re-enter that journey and immediately hit the If/Else, or would be blocked from re-entering the journey at all by each journey's own entry settings, was not checked this session — doing so would have required pausing a live journey to inspect its entry-settings, which was avoided as it's out of scope for a read-only audit of a live production automation.

## End-to-end suppression test — performed on staging, partially proven

A controlled, Andrew-authorized test was performed on 2026-07-16 using a dedicated non-admin, non-subscriber test contact (`suppression-test-contact-01`, a made-up address at the company's own domain — not a real customer) and a WP-CLI-created staging WooCommerce order (order #595, one Mariana Trench paperback, no real payment). Full method, fulfillment-safety reasoning, and results:

- **Fulfillment safety verified before testing, via code inspection not credentials**: the Bookvault WooCommerce plugin's only order-submission function (`bvlt_resendOrder()`, in `wp-content/plugins/bookvault/Bookvault.php`) is called exclusively from a manual single-order "Resend Order To Bookvault" action and a manual bulk "Resend Orders To Bookvault" list action — both require a human to explicitly click them in wp-admin. No hook anywhere in the plugin is tied to order-status changes. Neither action was ever invoked, so the test order could not have triggered a real print/fulfillment event regardless of status transitions.
- **An initial attempt (order #594) using an `@example.com` test address was correctly rejected by Mailchimp's own API validation** ("This email address looks fake or invalid," Error 400) — `example.com` is a recognized placeholder domain and Mailchimp's server-side validation flags it. This order was cancelled and superseded by order #595 using a real company-domain address with a made-up local-part, which passed validation.
- **Purchase-tagging: PROVEN.** The order transitioned to Processing, synced to Mailchimp automatically (~90 second queued delay, confirmed in the plugin's own log), and `Global - Tag Purchasers` automatically applied the `Customer - Purchased` tag to the contact — confirmed via the automation's own Flow Data (1 started, 1 completed, tag added: 1) and independently via the Tags contact-list view.
- **Journey-condition configuration: PROVEN.** The Educators journey's If/Else condition reads exactly `Tags > contact is tagged > Customer - Purchased` — the identical tag now confirmed present on the test contact. Inspected directly via the Segment Builder panel (read-only, cancelled without saving any change) rather than assumed from prior documentation.
- **Branch execution: NOT proven, by design.** Proving that a tagged contact is actually routed to the Yes-branch/exit in practice would require activating the Educators (or any) acquisition journey and letting the real contact traverse it — the directive explicitly prohibits activating any acquisition journey for this test. This is the one link in the chain that remains unproven, exactly as anticipated by the directive's own fallback instructions ("prove automatic tag application, prove the journey condition is configured to that same tag, document that branch execution itself remains untested").
- **Conclusion**: Email 3 suppression is proven for two of its three links (automatic tagging, condition configuration) via direct, live, non-admin evidence. The third link (branch execution inside an active journey) cannot be proven without activating a journey, which stays out of scope. The smallest remaining step to complete full end-to-end proof is a single-journey activation test with the same test contact, explicitly authorized by Andrew when he is ready to move a specific journey toward launch.
